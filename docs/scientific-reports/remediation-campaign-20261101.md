## What the current system actually executes

The standard production path preserves separate Judge-entry, Planner, Data
Acquisition/Audit, Preprocessor, Training Engineer, Runtime Monitor, Evaluator
and Judge-exit owners, all 45 native operations, persistent memory and action
receipts. It can execute real services supplied to the staged composition.
The new CPU profile supplies actual data validation/preprocessing, model
selection, optimization, monitoring, development evaluation and finite
adaptive decisions. It uses the existing `ProductionLoopRunner`,
`StagedProductionCycleDriver` and real Hugging Face lifecycle rather than a
scripted fake trainer or a monolithic replacement for role boundaries.

Continuation checks a retained, lineage-bound checkpoint identity before any
unapplied lineage mutation. Prepared recovery shares those checks. Host-local
kernel ownership fences concurrent invocation, with durable started/returned
receipts; an ambiguous external effect is blocked, not blindly repeated.
Healthy pending polls no longer consume failure budget. Host-local ownership
does not supply distributed cross-host fencing.

The operational recovery bridge preserves a terminal failed workflow and
creates one bounded new attempt only when actual retained optimizer evidence
proves zero updates and no update ever started, and existing recovery policy
admits it. The new attempt preserves scientific configuration, with a new run
identity and the named operational fault removed. In-flight/post-update
failures, OOM, missing evidence, corruption and unknown outcomes do not use
this automatic bridge. File and directory fsync precede optimizer updates.

The CPU program can choose the next learning rate inside its frozen finite
grid, warm-start an accepted adapter with explicitly reset optimizer state,
reject a candidate while retaining its parent, recover an admitted bootstrap
failure and stop at the cycle cap. Default staged branch/restart/rollback,
stage/curriculum/data-policy changes and arbitrary code edits lack automatic
next-experiment handoffs and are explicitly excluded. Standalone governed
state APIs retain their own approval requirements. No claim of full automatic
pretraining or unrestricted repair follows from their action names.

The [supported-execution guide](../operations/supported-execution.md) contains
tested CLI routes, API/caller distinctions, inactive TODO scaffolds and the
storage constraint. The console remains a bounded legacy inspection/demo
surface. Frozen five-role CUDA inference belongs to its specialized governed
composition; this CPU comparison did not invoke those specialist models.
Ardor has contracts and fake-runner tests, without an authenticated real
Ardor repair or demonstrated live endpoint.

therefore could not certify the ninth publication; the summary was not used
to manufacture its missing historical completion. This cohort is excluded.

Investigation separately reproduced a reader lifetime defect: with cyclic GC
disabled, 200 reads retained **401 extra file descriptors** because a connection
context manager does not close its connection. #178 closes all readers/error
paths; the same probe retains **zero**. It adds read-only readiness/integrity,
consistent snapshots and deduplicated retained evidence. However workspace
cohort v2 failed with corruption after its first completed program even with
the reader repair. Neither cohort is an accepted comparison.

The corruption's ultimate cause is **unassigned**, tracked in open
[#179](https://github.com/kys928/Hephaestus/issues/179). SQLite3.53.1 already
contains the older WAL-reset fix; that old defect is not assigned as cause.
A small isolated four-thread/2,400-record stress test passed, followed by the
complete isolated v3/cold proof above. Those results support this bounded
storage choice, not a general cure or causal attribution to synchronized
storage. Active research databases must remain outside synchronized workspace
trees for this profile. Long-lived reliability is still a material limitation.
