# Public Smol feasibility pilot v1 — permanently nonconfirmatory

This plan precedes execution. The pilot is for generation diagnostics, design
feasibility and power planning. It is never confirmatory improvement evidence.
No final protected batch, seed, commitment, key, unlock or one-use final session
is obtained. Run only after the Mission A bounded CPU storage boundary has passed
its campaign endurance/restore verification. Use no paid infrastructure.

## Frozen generation and measurement

The prospective public contract is `smol-public-json-cap128.v1`: original pinned
instruction-chat template and unchanged JSON-only system instruction, explicit
attention masks, greedy batch-one decoding, one beam, CPU float32, max 128 new
tokens, min zero, EOS/pad ID 2, no forced EOS/BOS, no repair or filtering. Construct
a new GenerationConfig so model repository defaults cannot add stopping rules.
Retain exact prompt IDs/hash, generated IDs, raw uncleaned text, real EOS status,
truncation and target IDs. The endpoint requires actual EOS plus the existing
finite, duplicate-key-rejecting, exactly typed JSON scorer. Nontermination is
incorrect even if the text parses. Also report typed exactness separately.

On the 24 original public development cases only, evaluate baseline and historical
public adapter with budgets 16, 64 and 128, retaining all attempts. These are cap
diagnostics; the public pilot budget is already fixed at 128. Each fresh candidate
uses 128 on development. Select the prospective best-of-three procedure solely
by development terminated exact count, then development valid JSON count, then
lowest training seed. Pilot scores never select a seed or retune decoding.

At 128, evaluate baseline, historical public adapter and all three fresh seeds on
all 96 pilot surfaces. Report terminated/typed exactness, valid JSON, EOS,
truncation, length distribution, target NLL including EOS, family effects,
difficulty characteristics, paired wins/losses and wrapper sensitivity. Keep
primary canonical and secondary wrapper results separate in power planning.
No pilot p-value certifies improvement. Small paired counts give wide uncertainty.

## Technical restart and external checkpoints

The measurement plan and generation budgets remain unchanged. Contract v2 adds
technical phase checkpoints after an actual temporary-runtime loss erased an
unpublished attempt. That lost attempt cannot supply accepted raw evidence.
Preserve its observed disposition; a fresh run is a new attempt, not a recreated
historical completion.

`--pause-after-training` stops only after the three 96-update candidates and the
independent 96-update repeat have complete verified checkpoints. `resume` requires
the separately retained contract digest, original source installation, all three
seed/job bindings and exact repeat proof. It launches no optimizer and never
reconstructs missing training. Pure fixed public measurements are retained under
keys binding model, input, cap, source/plan and development-bucket identity.
Restart reuses acknowledged raw receipts and computes only missing public
measurements. Unknown SQL acknowledgement is reconciled by the campaign witness.
This mechanism rejects confirmatory purposes and final bucket-9 identities; it
never supplies a final exposure permission.

`--checkpoint-root` publishes sealed complete phase snapshots and a separately
retained control-journal copy. These remain temporary until exported to external
retention. Save the training-ready checkpoint before long generation, then save
subsequent completed phase checkpoints. Restore at the same logical absolute
paths with the externally retained latest journal/manifest commitment. Missing
control history remains blocked. Phase timing measures the current generation
invocation; training and external pauses are reported separately.

This pilot's outcome determines whether a revised final protocol is worthwhile.
It does not supply independent design acceptance, an independent exposure ledger,
custodian authorization, a final protected batch, or resource spending approval.
